### R01 · [x] Withdraw tx builder drops non-cbBTC deposit reserves from post-refresh, breaking withdraw for mixed Kamino obligations

- **위치**: `src/services/KaminoTxBuilder.ts:470` · 차원 bugs · 노력 small
- **문제**: buildWithdrawTransaction computes the post-withdraw reserve list as `remainingDeposits = afterCollateral > 0n ? [reserve] : []` plus borrow reserves (lines 466-471), i.e. it assumes cbBTC is the ONLY deposit in the obligation. But the obligation PDA is the standard vanilla tag-0/id-0 obligation (deriveObligationPda, KaminoService.ts:167-182) shared with the Kamino web app's main market. If the user has any other deposit there (SOL, JitoSOL, USDC supplied via kamino.finance), the post-withdraw refreshObligation is built with a wrong remaining-accounts list. Per the code's own documented invariant (KaminoTxBuilder.ts:190-191: reserve list must match the on-chain obligation's reserves or the instruction fails with 6006), the whole atomic tx reverts, so the pre-sign simulation gate in useWithdrawLending throws and withdrawal via the app is impossible for those users (funds only recoverable via Kamino web). Additionally `willClose = postReserves.length === 0` (line 474) is wrong for the same case: with another deposit and no borrows, it skips the post-refresh believing the obligation closes when it actually stays open.

This preserves other deposit reserves in obligation order (deposits then borrows, as collectObligationReserves already returns). Add a unit test with an obligation fixture containing a second deposit reserve.
- **검증**: Confirmed in code. KaminoTxBuilder.ts:470 rebuilds the post-withdraw refreshObligation reserve list as `afterCollateral > 0n ? ### R02 · [x] Liquidation price mixes fresh cbBTC price with stale obligation LTV — risk display wrong exactly when price moves

- **위치**: `src/services/KaminoService.ts:144` · 차원 lending · 노력 medium
- **문제**: mapObligationToPosition computes currentLtv/liquidationLtv from obligation aggregates (depositedValueSf, borrowFactorAdjustedDebtValueSf, unhealthyBorrowValueSf) that are only updated on-chain at the last refreshObligation (typically the user's own last tx), then passes a FRESH reserve price into liquidationPrice(cbbtcPriceUsd, currentLtv, liquidationLtv) (KaminoService.ts:219,144; utils/lendingMath.ts:44-55). For fixed debt and collateral amount the true liquidation price is P_lastRefresh × currentLtv/liqLtv — i.e. price-invariant. Using P_now scales the reported liquidation price by P_now/P_lastRefresh: if BTC dropped 10% since the obligation was last refreshed, the app under-reports the liquidation price by 10%, telling the user they have more buffer precisely during a drawdown. Health factor, borrowedUsd (missing accrued interest since last refresh), and maxBorrowableUsd shown in EarnScreen/PositionDetail have the same staleness. Since Phase 2 deliberately relies on UI emphasis instead of notifications for liquidation risk, this display being wrong under price movement undermines that design.
- **수정안**: Recompute position client-side from raw per-slot data like the official SDK: deposited cbBTC = deposit.depositedAmount × cToken exchange rate (available/borrowed from the reserve, already fetched) × current price; debt = borrow.borrowedAmountSf adjusted by (reserve.cumulativeBorrowRate / borrow.cumulativeBorrowRateSnapshot). At minimum, stop mixing: compute liquidation price directly as debtUsd / (collateralCbbtc × liqThreshold) so it does not shift with the display price. All computation stays client-side (no backend needed).
- **검증**: Confirmed in code. KaminoService.ts getUserPosition (line 219) takes a fresh reserve price (marketPriceSf, refreshed near-continuously on the active Kamino main market) and mapObligationToPosition (lines 122-129, 144) combines it with LTV ratios derived from obligation cached aggregates (depositedValueSf, borrowFactorAdjustedDebtValueSf, unhealthyBorrowValueSf) that are only updated on-chain by refreshObligation — in this app, only appended to the user's own txs (KaminoTxBuilder, cf. plan.md:608). Math verified: displayed liquidation price = true price × (P_now/P_lastRefresh), so a 10% BTC drop under-reports the liquidation price by 10%; healthFactor and riskZone are fully frozen at the last-refresh price and never react to price moves between user txs. No compensation exists: useKaminoPosition is a plain read-only query and EarnScreen PositionDetail renders the values directly with no staleness handling. Not a deliberate policy — plan.md:608 shows staleness was only patched for the just-deposited case; the suggested fix is entirely client-side (no-backend policy intact). Severity stays high because Phase 2 deliberately relies on this UI emphasis (no notifications) as the sole liquidation-risk mitigation, and the display is wrong precisely during drawdowns when liquidation (with real penalty) threatens; the raw data for correct client-side recomputation is already decoded in KaminoTxBuilder.ts:373-381.

- **검증**: Confirmed, not refuted. ## 기각된 발견 (참고)

- **waitForConfirmation treats a transient RPC error as fatal, aborting the cbBTC Lightning payment mid-flow** (bugs): The premise (no try/catch around getSignatureStatuses at useCbbtcLightning.ts:139) is true, but the claimed harm is refuted: the caller already handles this case. LightningScreen.tsx sets a `swapped` flag when onPhase("confirming") fires — which happens before waitForConfirmation is called — and its onError handler uses `afterSwap = swapped || timedOut` (line 321), not error-string matching. Any error during confirmation, including a raw RPC 429/network throw, therefore shows the purpose-built "lightning.cbbtcRetryWithUsdc" notice, auto-switches the source token to USDC, and suppresses the raw error message (setLastError evaluates to null since noticeMsg is truthy). The user gets exactly the "retry with USDC" guidance the finding claims is bypassed; no funds are at risk. The only residual benefit of the suggested fix is that a payment might complete end-to-end without a manual USDC retry, but the triggering condition (all three failover endpoints failing in one rotation) typically means the radio is fully down, in which case the subsequent Atomiq LN step would fail too. A minor resilience nicety, not a bug worth fixing for this project.
- **Received-but-unclaimed FROM_BTCLN swaps are never discovered: app never calls getClaimableSwaps, so a payment that arrives while the app is killed/cancelled is silently lost to the receiver** (lightning): Refuted on the core mechanism. The SDK's getClaimableSwaps only returns FROM_BTCLN swaps in state CLAIM_COMMITED (\_claimableSwapStates = [CLAIM_COMMITED] in FromBTCLNWrapper.js:66, plus isClaimable() requiring CLAIM_COMMITED in FromBTCLNSwap.js:309-311). Every scenario the finding cites (app killed while QR shown, cancel-waiting at LightningReceivePanel.tsx:131-140, waitForPayment throwing) leaves the swap in PR_CREATED/PR_PAID, which getClaimableSwaps never returns — the app only calls commitAndClaim after payment confirmation (AtomiqProvider.ts:490-499). So the suggested fix (claimAll backed by getClaimableSwaps) would find nothing in those cases. The 'permanently lost funds' framing is also wrong: unclaimed HTLC swaps expire and the payer is auto-refunded by the LN protocol — a failed payment, not fund loss — which the comment at LightningReceivePanel.tsx:128-130 documents as the deliberate accepted outcome, consistent with the project's non-custodial/no-backend policy (offline receive guarantees would need an always-online claimer). The only real residual gap is the rare seconds-wide window where the app dies between commit confirmation and claim inside commitAndClaim (swap stuck at CLAIM_COMMITED, recoverable via getClaimableSwaps but undiscovered); even then all parties are auto-refunded on expiry. That narrow polish item does not support the finding as written or its high severity.
- **Lightning send path leaks raw untranslated err.message despite the app's own central friendly-error mapper** (ux-i18n): The cited code is real, but the behavior is a deliberate, documented decision, not a leak. Commit 6775b88 — the same commit that introduced toFriendlyErrorKey() — explicitly states: "LightningScreen's lastError box is intentionally left raw — it's the labelled, long-press-to-copy debug affordance (same as Earn), not an unframed leak." The finding misreads the UX: the raw err.message is never the primary message — failures show a translated toast (t("lightning.payFailed")/t("errors.userCancelled")) and the error box leads with a translated title plus copy hint ("결제 실패 · 길게 눌러 복사"), with the raw text as a selectable debug detail underneath (essentially the finding's own suggested secondary-detail structure). Common cases (user cancel, auth failure, wallet timeout, post-swap retry) are already intercepted at lines 318-331/414-418 and suppress the raw box entirely, and quoteErrorMessage maps all LightningQuoteError codes and amount errors to i18n before the fallback. The identical framed pattern is used in all four EarnScreen flows, so this is consistent app policy rather than a contradiction with the receive panel (whose fixed leaks were unframed notices).
- **EarnScreen (1533 lines) duplicates the entire tx-flow orchestration 4x across Supply/Withdraw/Borrow/Repay forms** (architecture): The 4-form structural similarity is real, but the finding's harm claims are refuted by the code. (1) The cited "drift" (SupplyForm's gasThreshold at EarnScreen.tsx:337-339) is a deliberate, commented decision: first supply creates obligation/metadata/farm accounts requiring more SOL rent, so only supply uses FIRST_SUPPLY_GAS_THRESHOLD_LAMPORTS — intentional divergence, not drift. (2) The "fix in four places" risk was already addressed: the error-hint ladder is centralized in src/utils/earnNoticeHint.ts, whose header comment explicitly says it was extracted because the four forms duplicated it ("네 개 폼이 동일한 ladder... 순수 함수로 묶어 단일 출처 + 단위 테스트 대상"), and cancel semantics live in the unit-tested useCancellableSign hook; LendingResultCard, LowSolGasWarn, and TxProgressModal are already shared. Remaining per-form code is ~30 lines of mechanical setState glue plus genuinely divergent behavior (borrow consent modal, withdrawAll/repayAll, repay's USDC-shortfall and dust-6092 handling, oracle-stale retries, different mutation payloads), so the proposed single hook would need per-form escape hatches and saves far less than the claimed ~400 lines. (3) The CLAUDE.md layering claim misreads the rule: SDK calls live in hooks/services; the duplicated code is UI-state orchestration, a presentation concern. Refactoring shipped, production-hardened cancel/token-guard code for DRY alone is not worth the regression risk here.
- **LightningScreen send path re-implements cancellation guard and error mapping that were already extracted for sharing** (architecture): Factual observations check out, but the core claims are refuted by deliberate, documented design. (1) useCancellableSign.ts:7 documents that the pattern was extracted FROM Lightning send for Earn/Swap/Receive; Lightning send needs more than the hook offers (payAbortRef actually aborts LP polling — explained at LightningScreen.tsx:248-250), so non-adoption is a known constraint, not drift, and token semantics are identical (no behavioral difference). (2) friendlyError.ts:1-3 explicitly scopes toFriendlyErrorKey to Lightning receive/refund/history — the codebase deliberately keeps separate ladders (toFriendlySwapError for swap, pickEarnNoticeHintKey for Earn); Lightning send's inline ladder handles cases the central mapper cannot (afterSwap→USDC retry + source auto-switch, quote_expired reset, raw err.message fallback vs errors.generic). Only the earn.\* key-namespace borrowing is a real nit, and it mirrors Earn's own ladder. (3) The 'behavioral gap' premise is wrong: WalletReconnectBanner renders only in EarnScreen (line 141) and SwapScreen doesn't call markAuthFailureNow either — marking is Earn-local by design, not a shared path Lightning missed; the 12h time signal in walletAuthAge.ts already covers the common auth-expiry case, and Lightning shows an immediate reconnect hint. Remaining value is a cosmetic i18n-key refactor, below the fix bar for this project.
